# 按策略配置模型调度

管理端「调度策略 → 调度配置」按配置组织模型，不再逐个模型编辑和保存。

1. 先选择调度范围「全部模型」或「区分模型」。「全部模型」只显示一套调度设置，不显示模型选择和「添加配置」，保存后自动包含以后新增的模型。
2. 「区分模型」下，在表单内展开适用模型列表并勾选模型，再设置调度优先级（Provider / Key）和调度策略（缓存亲和、负载均衡、固定顺序）。搜索只过滤模型列表，其他配置已占用的模型默认隐藏；通过取消勾选移除模型。选择框显示已选名称或数量，不重复显示已选标签。
3. 设置此配置共用的提供商 / Key 排序。实际请求仍只使用该模型可用的候选，不会因为共用排序而启用不支持该模型的提供商。
4. 「区分模型」下，点击调度配置标题旁的「添加配置」，为剩余模型选择不同策略。收起的配置直接显示适用模型名称，已分配给其他指定配置的模型不能重复选择。
5. 点击页面顶部「保存」统一生效，不需要逐个模型另存草稿。指定范围为空时不能保存。

## 范围语义

- 「全部模型」是独立的动态范围，不是勾选当前列表的快捷操作，保存后也自动适用于之后新增的模型。「区分模型」的列表不提供「全部模型」选项。
- 「全选当前」与「全选结果」只批量勾选当前可选模型，仍属于指定模型范围，不自动包含以后新增的模型。
- 编辑期间切换范围会分别保留两种模式的草稿，切回后恢复原有选择和设置。首次切换时继承当前配置的调度和排序；从多配置首次切到全部模型时，优先继承默认配置，否则使用第一条配置。保存只写入当前模式，全部模型模式会清除模型级的自动生成规则和独立排序。
- 旧数据中的指定模型与全部模型混合配置按「区分模型」加载，原全部模型条目显示为「默认配置」。默认排序仍可被各模型继承并覆盖，且不妨碍为剩余模型添加配置。
- 没有全部模型配置时，未指定的模型继续使用已保存的默认调度设置，不会被禁用。先修改配置再改为指定范围，不会把修改后的调度模式应用到未选择的模型。
- 移除模型或删除配置会同步移除对应的排序覆盖和自动生成的调度规则。
- 故障转移、首个候选重试次数和客户端断开处理等仍作用于整个调度策略，不随模型范围拆分。

## 存储兼容

无需数据库迁移，继续使用 `default_policy`、`model_policies` 和 `rules`：

- 全部模型的调度模式写入 `default_policy`，排序写入 `model: "*"` 的模型策略。
- 指定范围的共用排序展开为各模型的 `model_policies`；同一配置使用一条 `ui_scheduling_policy:` 前缀的调度规则，通过 `conditions.any` 匹配适用模型，并使用 `set_scheduling` 设置调度模式。
- 旧的逐模型排序和 `ui_model_scheduling:` 规则仍可读取；编辑调度配置时转换为新结构。等价的旧模型配置可合并显示，已有自定义规则和全局故障转移设置保留。
- 新建的不同配置即使调度设置相同，也保留独立的配置范围，重新打开页面后仍可分别编辑。

## 策略分组的选择顺序

请求使用的调度策略按以下顺序确定，先命中者生效：

1. 请求头 `x-aether-scheduler-group` 显式指定，且该主体被允许显式选择。
2. API Key、用户、用户组的默认绑定（该功能已实现但暂无界面）。
3. **模型级回退链**：按列表顺序（最上方为 0）找到第一个配置了该请求模型的分组。
4. 系统默认分组。

第 3 步的判定标准是「分组存在匹配请求模型的模型级策略」。「全部模型」配置写入的通配策略不算命中，因此它不会因为排在前面就接管所有模型。停用的分组保留在列表中的位置和编号，但不参与回退链，也不作为系统默认。

列表顺序因此同时是模型级分组的优先级，与启用状态无关：

- 列表按顺序编号 0、1、2…，最上方的编号 0 高亮显示。
- 新建的策略固定插到最前，其余分组顺延，与保存时是否已启用无关。
- 拖动可调整顺序，允许跨启用／停用状态拖动，保存后按新顺序生效。
- 「系统默认」标记始终由管理员手动指定，不随顺序变化。只针对某个模型的分组无需设为默认，放在默认分组之前即可只接管该模型。

## 链路预览与请求执行顺序

模型详情中的链路预览是**当前模型静态基线**，不是某次请求的执行记录：

- 预览按上述选择顺序确定分组：优先显示该模型命中的模型级分组，没有时回退系统默认分组；接口在 `effective_policy.source` 中区分 `model_chain` 与 `system_default`。
- 优先级使用应用策略覆盖后的有效值，包括 Provider、Key 和号池覆盖，不再仅显示提供商目录中的原始优先级。
- 预览复用路由策略解析器，应用全部模型／模型级配置以及仅依赖模型条件的规则，包括界面生成的模型调度规则。
- 依赖请求头、请求体、用户、API Key 或 API 格式的规则不在静态预览中猜测执行；若此类规则可能提前终止规则处理，后续不确定的规则也会被排除。接口通过 `effective_policy.rules_excluded` 披露排除数量。
- 无有效分组或解析失败时，回退目录优先级，并在策略元数据中说明。绑定、客户端模型别名和请求上下文可能产生不同结果。
- 所有候选（包括首个候选）直接显示实际生效的优先级，例如 P1、P2；标签不是执行序号，不保证该节点一定先执行。

请求详情的链路追踪展示**真实尝试顺序**：

1. 新的 HTTP 候选循环记录在 `extra_data.execution_index` 中保存请求内执行序号；候选排名 `candidate_index`、`ranking_index` 和重试编号保持原义。
2. 整条时间线的已尝试记录都有合法且唯一的执行序号时，按执行序号排序；历史记录、WebSocket 等缺少该字段的路径按 `started_at` 排序。同一时间或缺少时间时以候选顺序稳定排列。
3. 先对尝试排序，再合并连续的同 Provider／同号池尝试。`A → B → A` 保留三个节点，不因提供商相同而把后一次 A 移到 B 前面。
4. 未启动和跳过的候选在未执行区域展示，不混入实际请求序列。尝试详情显示该次请求记录的策略分组名称，不展示执行序号和调度排名。历史记录没有分组名称时显示“未记录”，不使用当前默认分组代替。链路预览在优先模式右侧显示其使用的策略分组名称。

执行序号是进入执行流程的次序，不证明上游已经建立连接或返回响应。此次展示修复不修改实际候选排名、缓存亲和、负载选择或失败重试策略，也不回填历史执行序号。无需数据库迁移，新增字段通过现有候选 JSON 元数据存储。

排查预览与实际执行不同的请求时，先看时间线上的尝试顺序和策略分组，再核对分组顺序、模型级策略与绑定；需要进一步诊断时，可查看候选元数据中的执行序号和调度排名，再检查实时亲和及目标选择。不要仅凭预览位置推断上游请求的先后，也不要把计费标签“免费”当成路由选择原因。
